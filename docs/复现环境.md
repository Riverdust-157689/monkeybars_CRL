# 复现环境（换机器跑）

本文是"把仓库拿到另一台机器上、从零把环境和数据准备好、跑出同样的东西"的清单。
一句话版本：

```bash
git clone <repo-url> && cd monkeyBars_CRL && tools/setup_env.sh
```

---

## 1. 硬件 / 系统要求

| | 训练（GPU） | 回放 / 工具链（CPU 亦可） |
|---|---|---|
| GPU | NVIDIA，**CUDA ≥ 12.3**（MJX-Warp 要求），显存 ≥ 8 GB（本项目实测 4060 8 GB 可跑 128 world） | 不需要 |
| CPU | 任意 x86_64 | 任意 |
| Python | 3.10（本项目用 3.10.12） | 同 |
| 依赖 | 见 `requirements.lock.txt`（89 个包，全部钉版本） | 同 |
| 注意 | `jaxgcrl` **不在**依赖里：它是 vendored（`third_party/jaxgcrl/`，靠 `sys.path` 导入）。装 PyPI 的 jaxgcrl 会带进它自己的旧 pin `mujoco-mjx==3.2.7` 并与我们用的 3.13.0 冲突 | 同 |

* **GPU 机器上还需要 pip 版 CUDA/cuDNN**：`uv pip install -r requirements-gpu.txt`
  （原开发机用的是**系统级** CUDA/cuDNN，所以主 lock 里没有 `nvidia-*`；新机器若缺 cuDNN，
  JAX 会打印 `Unable to load cuDNN` 并**静默回退 CPU**）。`setup_env.sh` 现在会自动检测并补装。
  自检：`.venv-warp/bin/python -c "import jax; print(jax.devices())"` 必须出现 `CudaDevice`。
* 关键版本：`jax/jaxlib 0.6.2`、`mujoco 3.13.0`（自带 `mujoco.mjx` 与 MJX-Warp 后端）、
  `warp-lang 1.17.0`、`flax 0.10.7`、`optax 0.2.8`、`brax 0.12.1`、`numpy 1.26.4`（**必须 <2.0**）。
* 环境在 `.venv-warp/`（不进仓库）。`requirements.txt` 是直接依赖，`requirements.lock.txt` 是完整钉版。

## 2. 逐步复现

```bash
# 2.1 python 环境（uv 或 venv 均可）
uv venv --python 3.10 .venv-warp
uv pip install --python .venv-warp/bin/python -r requirements.lock.txt
#   或：python3.10 -m venv .venv-warp && .venv-warp/bin/pip install -r requirements.lock.txt

# 2.2 JaxGCRL：vendored（随仓库一起来，无需 clone/patch）
ls third_party/jaxgcrl/jaxgcrl/agents/crl/crl.py     # 存在即 OK
#     出处/差异/重新同步步骤：third_party/jaxgcrl/PROVENANCE.md
#     （可选）与上游核对（需要网络）：
#     tmp=$(mktemp -d); git clone https://github.com/MichalBortkiewicz/JaxGCRL $tmp/j
#     git -C $tmp/j checkout 5a6e7a0 && git -C $tmp/j apply $PWD/patches/jaxgcrl_crl_losses.patch
#     diff -r --exclude=assets --exclude=__pycache__ $tmp/j/jaxgcrl third_party/jaxgcrl/jaxgcrl

# 2.3 Unitree G1 网格：已随仓库提交，只需校验
find assets/g1_brachiation/menagerie/unitree_g1/assets -type f | wc -l   # 期望 51
( cd assets/g1_brachiation/menagerie/unitree_g1 \
  && find assets -type f | LC_ALL=C sort | xargs sha256sum | sha256sum )  # 见 menagerie_assets_hash.txt

# 2.4 静态检查（每次上 GPU 前都跑）
.venv-warp/bin/python src/check_args.py
.venv-warp/bin/python src/check_metrics.py
.venv-warp/bin/python src/check_variants.py   # 13 个 goal 变体的 state/goal 形状自洽
```

`tools/setup_env.sh` 就是上面 2.1–2.4 的封装，并且额外**从源码重建场景并与仓库里的 XML 对比**
（`nq/ngeom/bar_x` 必须一致），保证"程序化生成的资产"是可复现的。

## 3. 仓库里没有的东西

| 内容 | 大小 | 获取 | 校验 |
|---|---|---|---|
| `.venv-warp/` | ~1.2 GB | `tools/setup_env.sh` | `requirements.lock.txt` |
| `third_party/jaxgcrl/` 的其余部分 | 78 MB（上游 `.git` + benchmark 网格等） | 不需要；只看 `PROVENANCE.md` | — |
| `assets/g1_brachiation/menagerie/` | 38 MB | **已提交进仓库**（`git clone` 即有）| `menagerie_assets_hash.txt`（网格）/ `menagerie_sha256.txt`（上游 XML）|
| `.scratch/jaxgcrl_upstream_git/` | 23–34 MB | upstream 的 git 对象库，**只被 `tools/make_patch.sh` 用**；新设备一条命令恢复：`tools/make_patch.sh --restore-upstream`（克隆 `MichalBortkiewicz/JaxGCRL@5a6e7a0`，需网络）| 恢复后 `tools/make_patch.sh --check` 必须打印 byte-identical |
| `runs/`（结果） | 数百 MB | 自行 `rsync -av runs/` 从跑过的机器搬；**不需要**也能重新训练 | 每个 run 的 `args.json` 里有 `git_commit` + 全部超参 |

> **`.scratch/` 是什么**（2026-09-21 补充）：gitignore 的本地草稿区。除 `jaxgcrl_upstream_git/` 外全是
> **一次性**东西——改代码用的补丁脚本（`patch_*.py`）、探针/调试脚本（`*_probe*.py`、`dbg*.py`）、smoke 日志、
> 以及写文档时先落盘的段落草稿（`s95x.md`）。它们的**结果都已提交**（代码补丁已应用并 commit，文档段落已并入
> `docs/`），所以**不同步到别的设备没有任何影响**。唯一例外是 `jaxgcrl_upstream_git/`：
>
> | 你要做的事 | 需要 `.scratch/` 吗 |
> |---|---|
> | 训练 / 评估 / 回放 / 三个 `check_*` 守卫 | **不需要**（vendored 源码 + `patches/*.patch` 都在仓库里）|
> | **应用** patch | 不需要 |
> | **重新生成 / 校验** patch | 需要：`tools/make_patch.sh --restore-upstream` |
>
> 缺对象库时脚本会**明确失败**（`--check` 退出 1、无参数退出 2），不再 `exit 0` 假装成功。
>
> ⚠️ 两个哈希都是**本仓库所有 run 使用的版本**。**只有网格影响物理**（已跟踪的
> `scene_bars*.xml` 通过 `meshdir` 引用它）；上游 XML 只在用 `build_scene.py` 重建场景时才读。
> 如果网格指纹不符，说明拿到的不是本仓库的模型 ⇒ 用 `git checkout -f -- assets/g1_brachiation/menagerie`
> 恢复，而不是直接跑。

## 4. GPU / MJX-Warp 的坑（都已踩过）

1. **Warp 的显存不在 XLA 池里**：`--xla-mem-fraction 0.70` 只限制 JAX，Warp 的缓冲另外分配；
   8 GB 卡上两者都要留空间。
2. **`naconmax` 是全局接触预算**：必须 `per_world × num_worlds`。训练与评估 world 数不同，
   所以 `train.py` 会分别设置（评估环境按自己的 world 数缩放），否则会出现"没报错但接触被悄悄丢弃"。
3. **replay buffer 是按 env 计的**：显存 ≈ `max_replay_size × num_envs × data_size × 4 B`。
   8 GB 卡上 `--max-replay-size 100000` 会 OOM；用 `--buffer-gb`（默认 2.0）会自动夹住并打印。
4. **`ls_iterations`**：场景 XML 里写死 20（MuJoCo 默认 50），M1 已验证；`--ls-iterations 50` 可做 A/B。
5. **`--smoke` 配置的 `critic_loss` 是 nan**：tiny 配置（4 envs / batch 100）本身会发散，
   baseline 代码同样如此（§9.34.5 的 A/B）。`--smoke` 只用于接线检查，不是数值健康检查。
   `train.py` 有 NaN 守卫：连续 3 个 eval 出现 nan 会打印并中止。
7. **GPU 原生段错误（`Segmentation fault (core dumped)`）—— 先怀疑整机 CUDA 栈，不要怀疑 goal 变体/超参**
   （2026-09-21 复现两次，均为同机并发两个 JAX+Warp 训练时）：

   症状：
   * `dmesg` 里 `ptxas[...]: segfault ... error 6`（宿主端 CUDA 汇编器野写）、
     `python[...]: segfault ... error 7 in xla_cuda_plugin.so`、
     `python[...]: segfault at 1 ip 0000000000000001 error 14`（跳到垃圾地址）；
   * 同时 `NVRM: ... NV_ERR_INVALID_OBJECT_HANDLE ... serverGetClientUnderLock() @
     rmapi_deprecated_control.c` **每 10 秒刷一条**（驱动里有个失效 client 句柄，典型来自共享算力/
     监控代理，或崩掉后残留的进程）；
   * Python 层**没有 traceback**（原生崩溃）。日志最后一行常停在 wandb 初始化后——因为 stdout 走管道时
     是**块缓冲**，缓冲区随进程一起丢；用 `python -u` 才看得到真正跑到哪一步。

   判据：**三个互相独立的进程**（ptxas + 两个 python）在几分钟内以"内存破坏类"错误崩掉 ⇒ 整机/驱动层，
   **与 goal 变体无关**。两次的实证：第一次崩的是早就跑通过的 `support_dual`；第二次 `dual6c` 在
   `--gpu 1` 正常、`dual6d` 在 `--gpu 0` 崩，而两者 state 都是 145、goal 都是 6，结构完全相同——
   **出问题的卡换了位置**（先前是 `--gpu 1` 崩），所以不是某张卡坏，而是整机驱动 + 并发。

   排查：
   ```bash
   sudo dmesg -T | tail -30                 # 找 segfault / Xid / NVRM
   journalctl -k --since "10 min ago" | grep -iE "segfault|nvrm|xid" | tail
   nvidia-smi ; nvidia-smi -q -d PIDS | head -40     # 另一张卡上的任务还在吗？有无残留进程
   env | grep -iE "preload|^LD_|soll|cuda"           # 注入库 / 共享算力代理
   .venv-warp/lib/python3.10/site-packages/nvidia/cuda_nvcc/bin/ptxas --version   # 纯 host 工具，不碰 GPU
   ```

   处置（按序）：
   1. 停掉**所有** GPU 任务（并发是触发条件之一）；
   2. 复位驱动：`sudo fuser -v /dev/nvidia*` 确认无残留 →
      `sudo nvidia-smi --gpu-reset -i 0,1`，失败则
      `sudo rmmod nvidia_uvm nvidia_drm nvidia_modeset nvidia && sudo modprobe nvidia_uvm nvidia_drm nvidia_modeset`，
      最省事是**重启**；然后**空载观察 5 分钟**，`NV_ERR_INVALID_OBJECT_HANDLE` 必须停止刷屏；
   3. 复位后**单卡单进程**跑，确认 `[gpu] CUDA_VISIBLE_DEVICES=N jax.devices()=[CudaDevice(id=0)]`；
   4. 单进程仍崩 ⇒ 改用**系统 CUDA/cuDNN 模块**（只保留 `jax-cuda12-plugin` + `jax-cuda12-pjrt`），
      仍崩再查宿主内存（关 XMP / memtest）并找管理员。

   **实操结论：这台 dual4090 上宁可串行跑，也不要并发两个 128-env 训练**（A/B 各 1.5 h，串行只多花 1.5 h）。

6. **点 GPU 之外也能跑**：`JAX_PLATFORMS=cpu` 下 MJX-Warp 可以编译执行，
   够用于 `render_policy.py` 回放、`m3_swing.py`/`goal_geometry.py`/`check_scene.py` 等纯 MuJoCo 工具。
   例：`JAX_PLATFORMS=cpu MUJOCO_GL=egl .venv-warp/bin/python src/render_policy.py --ckpt runs/ckpt/actor_latest.pkl --episodes 4 --steps 400`

## 4.5 指定显卡

**唯一需要记的**：`CUDA_VISIBLE_DEVICES`。JAX 与 MJX-Warp 都通过 CUDA runtime 枚举设备，
所以这一个变量同时管住两边（被选中的卡在它们眼里是 `cuda:0`）：

```bash
CUDA_VISIBLE_DEVICES=1 .venv-warp/bin/python src/train.py ...   # 用物理 1 号卡
.venv-warp/bin/python src/train.py --gpu 1 ...                  # 等价（train.py 的便捷开关，
                                                               # 在 import jax/warp 之前设置）
JAX_PLATFORMS=cpu .venv-warp/bin/python src/render_policy.py ... # 纯 CPU（回放/工具）
```

启动时会打印一行确认：`[gpu] CUDA_VISIBLE_DEVICES=1 jax.devices()=[CudaDevice(id=0)]`。

* **多卡**：本实现是**单设备**（128 个 env 在一张卡上 vmap），所以"一张卡一个进程"——
  起 N 个进程，各自给不同的 `--gpu k`、`--exp-name ..._gk`、`--checkpoint-dir ..._gk`、`--seed k`。
  换更强的卡可把 `--num-envs` 提到 256/512（上游默认 512），吞吐随之上升，但
  `--buffer-gb` 与显存要跟着调。
* **显存**：`--xla-mem-fraction 0.70` 只限制 **JAX 的池**；**Warp 的缓冲不在这个池里**，
  共享卡上要给它留余量。若确实要共用一张卡，可加 `XLA_PYTHON_CLIENT_PREALLOCATE=false`
  （JAX 不预占、按需增长，代价是可能有重分配开销）。
* 别把 `--gpu` 与 `JAX_PLATFORMS=cpu` 混用（后者已经强制走 CPU）。

## 5. 怎么跑

```bash
# 训练（当前主线：M4 双持目标 support_dual；场景 full035 = 0.35 m 杆距）
.venv-warp/bin/python src/train.py --preset C_l2_infonce --num-envs 128 \
  --num-eval-envs 16 --batch-size 512 --min-replay-size 1000 --unroll-length 62 \
  --action-window reach --goal-variant support_dual --train-goal-bar 1 --eval-goal-bar 1 \
  --expl-hold 10 --num-evals 20 --steps 12200000 \
  --checkpoint-dir runs/ckpt_dual --save-every 5 \
  --impl warp --scene full035 --wandb --exp-name brach_dual_b1
```

**步数 ↔ 墙钟的换算**（实测吞吐 **8.387 M env-steps/h**，128 envs / unroll 62）：

$$\text{actual}=\Big\lfloor\tfrac{\text{steps}-128000}{\text{num\_evals}\cdot 7936}\Big\rfloor\cdot \text{num\_evals}\cdot 7936+134912$$

| 目标时长 | `--steps` | `--num-evals` | 实际步数 |
|---|---|---|---|
| 1.5 h | 12,200,000 | 20 | 12,197,632 |
| 4 h | 33,460,000 | 40 | 33,466,112 |
| 6 h | 50,300,000 | 60 | 50,131,712 |

其它入口：`src/render_policy.py`（回放/视频/`trace.csv`）、`src/check_reset.py`（reset 容差）、
`src/check_scene.py`（资产校验）、`src/goal_geometry.py`（goal 空间几何）、
`src/m3_swing.py`（IK/摆动可达性，纯 MuJoCo）。
